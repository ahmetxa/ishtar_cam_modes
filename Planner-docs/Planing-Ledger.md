# Planing Ledger

> Ledger v2 — ClaudeQB. Created by Step 2. Body language: English (default contract).

## 1. Purpose

This ledger is the durable record of planning and implementation continuity for `ishtar`. It exists so that a replanning run or a Step 4 implementation session can determine what was planned, what was applied, what was verified, and what remains blocked, without reconstructing that history from a conversation.

It is supporting evidence, not absolute truth. Where this ledger and the current repository state disagree, the repository wins and the ledger is corrected. Step 4 appends concise implementation summaries after verified slices or stop events; Step 2 and Step 3 update planning state.

The project's own history is the reason this file matters. Autopsy `AUTOPSY-P0-02` records a three-step misattribution caused by state not being captured before and after changes, and Project-Comprehension `QAS-03` records that findings deferred to later in a session are the ones lost to context truncation. A ledger that is written during work rather than after it is the countermeasure.

The primitive is therefore both effective and exactly reversible: `adb shell su -c 'touch /data/adb/modules/ishtar_cam_modes/disable && reboot'` returns the device to genuine vendor state, and removing the flag returns it to the precise prior state. Recovery is "do not mount", and it is provided by the root manager without executing any module code. **`Faz 9.2` does not need to be pulled forward.**

**The `Faz 3.3` precondition attached to that decision is confirmed, and it holds on both branches.** The condition was that the argument survives only if `Faz3.3` patches the module's `active_hal/` copy rather than writing `/odm` directly. `Planner-docs/Faz-3-Plans/Faz3.3-single-word-patch-and-metadata-proof.md:56` states that `hal_write` writes to `$MODDIR/active_hal/camera.qcom.so` "rather than to the live target". Independently, `/proc/1/mountinfo` shows the live `/odm` HAL *is* a bind mount of that same file, so the two addresses are one inode while the module is active, and with it disabled `/odm` is a read-only vendor mount where a stray write fails rather than damages. One caution carried forward from that same sub-plan at line 29: an experimental entry changes the copy's checksum, `hal_state` then classifies it `unknown`, and `hal_set` **re-seeds** it — so `Faz3.3` must account for the module undoing its own experiment.

**`FIND-2.2-01` (new, P2, open) — the v2.1 installer aborts any upgrade performed from a non-stock sensor mode.** `customize.sh:20` reads `md5sum /odm/lib64/camera/com.qti.sensormodule.ishtar_semco_imx989_wide.bin` and `customize.sh:23-27` aborts with "Muhtemelen OTA aldin. Blob'lar yeniden uretilmeli." unless it equals `9e4d0fe1a8bf2eb4146c9917a0ac2c4c`. Ikisi de gecerli sayilir" — and `customize.sh:40-44` accordingly accepts both the stock and the fullres checksum. **`FIND-2.2-02` (new, evidence) — the sensor mode is observable in the camera metadata, not only in the blob checksum.** The disable/enable pair moved two stream-configuration rows that nothing predicted: `camera.hal0`'s `4096 2304` and `4096 3072` entries read format `38` with the `dcgB` blob mounted and format `37` without it. Format codes are not asserted from memory — `agc-50mp-yama/hal-raw50-deneme.patch:5` records `0x25 RAW10, 0x26 RAW12`, i.e. `37` = RAW10 and `38` = RAW12, and `50MP-Entegrasyon-Plani.md:1210-1211` uses the same mapping. So the `dcgB` blob causes the main camera's two full-array entries to be advertised as **RAW12 instead of RAW10**, with the entry count unchanged at 440. This does not contradict IMPL-04's three-line `dcgB`->`dcgA` sensitivity result: both are DCG modes and both would advertise RAW12. It is the first observation in this project of a sensor-layer change that moves the *camera metadata* rather than only the blob identity, it gives `Faz2.3` a second discriminator per mode, and it bears on the AGC work, where `50MP-Entegrasyon-Plani.md:1063` records `pref_fix_resolution_key_N=37` selecting by exactly this format code. **`FIND-2.2-02`'s control experiment is answered: the RAW depth change is caused by blob content, not by mount presence.** IMPL-10 found the device already in the exact configuration the control required — `setmode.sh stock` applied, and `sensor.mount.count` still `1`.
