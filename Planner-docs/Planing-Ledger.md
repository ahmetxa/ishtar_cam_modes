# Planing Ledger

> Ledger v2 — ClaudeQB. Created by Step 2. Body language: English (default contract).

## 1. Purpose

This ledger is the durable record of planning and implementation continuity for `ishtar`. It exists so that a replanning run or a Step 4 implementation session can determine what was planned, what was applied, what was verified, and what remains blocked, without reconstructing that history from a conversation.

It is supporting evidence, not absolute truth. Where this ledger and the current repository state disagree, the repository wins and the ledger is corrected. Step 4 appends concise implementation summaries after verified slices or stop events; Step 2 and Step 3 update planning state.

The project's own history is the reason this file matters. Autopsy `AUTOPSY-P0-02` records a three-step misattribution caused by state not being captured before and after changes, and Project-Comprehension `QAS-03` records that findings deferred to later in a session are the ones lost to context truncation. A ledger that is written during work rather than after it is the countermeasure.

### IMPL-20 — Faz 3.3, the write site confirmed by measurement (2026-09-01)

**The result in one line: `pixelArraySize` now moves, on one word, reversibly — and the value the project spent two phases hunting was already sitting in the register it needed to be in.**

**The design question was answered statically, which is why this cost one attempt instead of several.** The handoff flagged an open question — nobody had established which offset in the sensor structure `S` holds `8192x6144` — and suggested tracing `InitializeScalerStaticCaps` to find out. The trace went one level further back, to the structure's *initializer* rather than its readers, which turned out to be decisive. Scanning `.text` for 32-bit accesses at the known sibling offsets found exactly one write region, `0x016f0330`…`0x016f0830`, and it states the relation in the clear: `[S+0x3db4] = [S+0x3c1c] / [x21+0x160]` and `[S+0x3db8] = [S+0x3c20] / [S+0x3d80]`, with the binning factor computed as `(int)sqrt([x27+8])` — `sqrt(4) = 2` for a 2x2 bin. `S+0x3c1c` is therefore the **unbinned** pixel array and `S+0x3db4` the **binned** one, and the displacement between them, `0x198`, is exactly candidate 2's immediate.

**That inverted the candidate ranking.** Candidate 1 (`0x01666440`, `mov w5, #0x3c1c`) was **withdrawn without being spent**: its immediate already points at the unbinned pair, so editing it moves away from the answer. Candidate 2, previously ranked second because "its effect is conditional", became the determinate choice — and the condition resolved itself. The reported `f0006` was `[4096 3072]`, which *is* the binned pair; had the selector been anything but `1`, the publisher's default path would already have been publishing `S+0x3c1c`. So the selector was `1`, `S+0x3c1c` already held `8192x6144`, and the value was being loaded into `x17` at `0x0166644c` on every single call and then immediately overwritten.

**A warning in the handoff was also refined.** "A patch must satisfy BOTH publication paths" is true of the *publications* but not of the *value write*: the second path (`0x016664b0`…`0x016664c8`) rebuilds the same tag and count and hands the trampoline at `0x1662098` the **same** `[x19+0x6550]` staging slot, deriving nothing of its own. Second, both resulting md5s were computed and **written into the patch table before the run**, so each write tested a prediction rather than recorded an outcome. Both matched.

**The third-md5 trap was handled by design, not survived by luck.** An experimental patch yields an md5 `hal_state` does not recognize, and `post-fs-data.sh` answers `unknown` by re-seeding from stock. Two consequences were planned for: the measurement was taken **without rebooting**, and `hal_set` was deliberately *not* used — the module's own reconciliation would have undone the experiment mid-run. The write instead mirrored `restart_camera`'s client-before-HAL ordering (invariant 3) in a temporary script, substituting a single `dd` for `hal_set`, and rewrote the contents of the already-mounted inode exactly as `setmode.sh:251` does for the sensor.
