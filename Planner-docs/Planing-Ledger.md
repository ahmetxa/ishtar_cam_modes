# Planing Ledger

> Ledger v2 — ClaudeQB. Created by Step 2. Body language: English (default contract).

## 1. Purpose

This ledger is the durable record of planning and implementation continuity for `ishtar`. It exists so that a replanning run or a Step 4 implementation session can determine what was planned, what was applied, what was verified, and what remains blocked, without reconstructing that history from a conversation.

It is supporting evidence, not absolute truth. Where this ledger and the current repository state disagree, the repository wins and the ledger is corrected. Step 4 appends concise implementation summaries after verified slices or stop events; Step 2 and Step 3 update planning state.

The project's own history is the reason this file matters. Autopsy `AUTOPSY-P0-02` records a three-step misattribution caused by state not being captured before and after changes, and Project-Comprehension `QAS-03` records that findings deferred to later in a session are the ones lost to context truncation. A ledger that is written during work rather than after it is the countermeasure.

**Half the address book for tag `f0006` was wrong, and that is the expensive half.** All **nine** recorded `movz`/`movk` sites are false positives — none of them builds `0xf0006`. Six load division magic constants (`0xffe56cb1`, `0xf83f630a`), one builds a 64-bit literal for a `stp`, and two load hashed keys. An exhaustive `.text` scan for the only encoding that can build the tag (`movz #6` + `movk #0xf, lsl #16`) finds **three** genuine sites, none of them among the nine. The six rodata dwords are the opposite case: genuine and provably exhaustive — they are the only six 4-byte-aligned `0x000f0006` dwords in the whole file — but **none is a value source**. They sit inside sequential tag-list runs or packed tuning data, and resolving every `adrp`+`add` in `.text` yields zero exact references to any of them.

**`H-01` is therefore contradicted, on both of its clauses.** The value is not written from a rodata dword, and nothing is reachable from the nine sites.

**What actually happens.** Inside the function starting `0x01661f40` (stripped; no symbol covers it), the HAL publishes the whole `android.sensor.info.*` family in sequence through the CamX metadata publisher at `0x1755430`. For tag `f0006` it loads sensor-data base `S = [x24+0x60]`, forms `S+0x3c1c`, reads selector `[S+0x3d84]` — the same field the address book already records with 55 accesses binary-wide — and copies the 8-byte `(width, height)` pair into the staging slot `[x19+0x6550]`, from `S+0x3c1c` or from `S+0x3db4` when the selector is 1. It then publishes that slot as tag `f0006` with **count 2** via `bl` at `0x0166648c`. Siblings in the same function corroborate the shape: `f0005` count 2 from `S+0x3dac`, `f000a` count 4 from `S+0x3d88`.

**F3.2-04 has a decisive answer: the value is runtime-derived, not a constant in the binary.** That is the fact `Faz3.2` flagged as potentially making a static patch infeasible. It does not — but it does determine the patch strategy, because there is no constant to edit.

**Ranked candidates handed to Faz 3.3.** (1) `0x01666440`, `mov w5, #0x3c1c` — one word whose immediate selects which pair in `S` is published; a genuine single-word change, conditional on confirming `S`'s layout on device. (2) `0x0166645c`, `ldr x1, [x4, #0x198]` — one word, but only on the selector-is-1 path. (3) Overwriting the load/store block with immediate construction of `8192x6144`; multi-word, alters control flow, ranked last.
